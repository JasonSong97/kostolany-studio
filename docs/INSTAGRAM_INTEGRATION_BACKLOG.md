# Instagram 실제 게시 연동 백로그

목표는 `kostolany.wisdom`에서 검수한 캐러셀과 릴스를 프로그램이 업로드·예약하고, 실제 게시 결과와 성과를 가져오도록 만드는 것이다. 기존 Buffer 호출 코드를 확장한다.

- 작성일: 2026-11-13
- 구현 기준: `2ee99c5` (`feat: initialize Kostolany content studio`)
- 대상: 본인 소유 Instagram 프로페셔널 계정 1개, 로컬 프로그램
- 현재 상태: 백로그 작성. 아래 추가 작업과 실계정 검증은 아직 완료되지 않음.
- 진행 방식: 우선 Buffer 경로로 완성. 저장소 제공자는 미정이며 IG-02에서 결정.

## 1. 현재 구현과 남은 차이

| 영역 | 현재 코드에 있는 기능 | 추가 작업 또는 검증 |
|---|---|---|
| 콘텐츠 제작 | 캐러셀 PNG·ZIP, 자막 릴스 MP4, 캡션, 파일 해시 생성 | 실제 게시 대상으로 파일 규격·표시 결과 확인 |
| 검수 | 제작 버전 승인, 원고 수정 시 승인·완성본 연결 해제 | 업로드와 예약 사이에도 같은 승인 버전을 유지 |
| 계정 연결 | `.env`의 API 키·채널 ID로 Instagram 채널 상태 확인 | 실계정 권한 확인, 계정명 표시, 선택 화면 |
| 미디어 전달 | 사용자가 공개 URL을 입력하면 검수 파일과 SHA-256 비교 | 파일 자동 업로드, 업로드 이력·URL 재사용 |
| 예약 | Buffer `createPost`, UTC 예약 시각, 게시 요청 기록 | 자동 업로드와 연결, 실계정 캐러셀·릴스 검증 |
| 중복·불확실 응답 | 기존 요청 중복 차단, 응답 불확실 시 `unknown`, 게시 ID 수동 연결 | 실패 단계별 복구, 재시작과 동시 실행 검증 |
| 게시·성과 조회 | 버튼으로 원격 상태·게시 링크·지표 저장 | 주기적 조회, 조회 오류와 게시 오류 분리 |
| 성과 분석 | 저장된 지표로 AI 분석 요청 | 실제 지표 제공 범위 확인, 비교 가능한 관찰 시점 관리 |

기준 코드: [게시 연동](../backend/publishing.py), [API와 RSS 반복 실행](../backend/main.py), [파일 생성](../backend/render.py), [DB와 작업 실행](../backend/core.py), [화면](../src/main.tsx), [기존 테스트](../tests/test_workflow.py).

기존 로컬 테스트 14개와 화면 빌드는 통과했다. 실제 OpenAI 응답으로 만든 콘텐츠, Buffer 계정 연결, Instagram 게시, 실제 성과 조회는 아직 검증하지 않았다. 로컬 테스트 성공과 실제 운영 완료는 별도로 기록한다.

## 2. 목표 흐름과 완료 단계

```text
영어 원고와 두 형식 제작
→ 완성본·캡션·출처 검수
→ 게시할 계정·형식·시간 확인
→ 승인 버전의 이미지·영상 자동 업로드
→ 업로드 파일 확인 후 Buffer 예약 요청
→ 예약 접수와 실제 게시 상태 추적
→ 게시물 링크·성과 기록
→ 다음 콘텐츠 기획에 반영
```

| 단계 | 완료 기준 |
|---|---|
| M1 실제 게시 | 공개 URL을 직접 입력하지 않고, 검수한 캐러셀 1건·릴스 1건을 각각 예약해 의도한 Instagram 계정의 실제 게시물로 확인 |
| M2 운영 자동화 | 앱 실행 중 게시 상태·성과를 자동 조회하고, 재시작 후 누락 조회를 복구하며, 미제공 지표와 조회 오류를 화면에서 구분 |

M1은 수동 상태 확인으로도 검증할 수 있다. 이번에 목표로 하는 운영 흐름의 완료는 M2까지 포함한다. AI 초안 생성과 실제 게시 승인은 기존처럼 사용자 실행을 유지한다.

## 4. 작업별 범위와 인수 기준

### IG-01 Buffer 실계정 연결과 게시 대상 확인

Buffer에 `kostolany.wisdom`을 연결하고 개인 API 키를 로컬 `.env`에 설정한다. 기존 `channel_info()`를 이용해 키 입력 여부와 실제 연결 성공을 구분한다.

- [ ] 사용자 로그인으로 프로페셔널 Instagram 계정 연결과 필요한 권한 허용을 완료한다.
- [ ] 채널 ID·계정명·플랫폼·연결 상태를 조회해 의도한 계정임을 확인한다.
- [ ] 키 누락·인증 실패·연결 해제·사용 불가 채널을 서로 구분해 안내한다.
- [ ] 실계정 연결 확인일과 결과를 기록한다. 키·토큰은 Git이나 검증 기록에 포함하지 않는다.

공식 근거: [Buffer Instagram 연결](https://support.buffer.com/articles/connecting-your-instagram-account-to-buffer-n9Ad6veXsu), [개인 API 키 설정](https://developers.buffer.com/guides/authentication.html). 계정 선택 화면은 IG-09이며, 첫 게시에는 현재 채널 ID 설정 방식을 사용할 수 있다.

### IG-02 미디어 저장소 선택과 설정 규격 확정

Cloudinary 또는 Cloudflare R2 등에서 첫 제공자 하나를 선택한다. 선택 전 특정 서비스 가입이나 유료 플랜 사용을 확정하지 않는다. 구현은 한 제공자로 시작한다.

- [ ] 제공자, 실제 사용 한도·비용 조건, 공개 파일 주소와 원본 보존 방법을 정한다.
- [ ] 필요한 환경 변수와 누락 시 오류를 정의하고 `.env.example`에는 빈 예제만 추가한다.
- [ ] 외부 로그인 없이 접근 가능한 HTTPS 주소를 만들고 예약 게시가 끝날 때까지 유지할 수 있다.
- [ ] 파일 자동 변환으로 기존 해시 비교가 깨지지 않도록 원본 전달 방식을 검증한다.
- [ ] 공개 업로드 대상은 승인된 최종 이미지·영상으로 한정한다. 책 원문·DB·키는 대상에서 제외한다.

Buffer API는 파일 자체를 받는 업로드 엔드포인트를 제공하지 않으며 공개 파일 URL을 요구한다. URL은 예약 시점 이후에도 접근 가능해야 한다. [공식 미디어 문서](https://developers.buffer.com/guides/hosting-media.html)

### IG-03 승인 파일 자동 업로드와 이력 저장

제작 결과의 manifest에서 파일을 가져와 선택한 저장소에 업로드한다. 기존 SQLite 자료를 보존하는 스키마 변경과 함께 업로드 이력을 저장한다.

- [ ] 기록에 초안 ID, 버전, 형식, 카드 순서, 파일 해시, 원격 객체 ID, 공개 URL, 상태, 시각을 포함한다.
- [ ] 캐러셀 카드 순서를 보존하고 릴스는 해당 버전의 MP4를 업로드한다.
- [ ] 같은 버전·파일을 다시 처리할 때 확인된 업로드를 재사용하며, 실패한 파일부터 재개할 수 있다.
- [ ] HTTP 성공만 보지 않고 공개 URL에서 원본 파일을 읽을 수 있는지와 해시 일치를 확인한다.
- [ ] 일부 파일만 업로드된 경우 예약 요청을 보내지 않고 진행 상황과 복구 방법을 보여준다.
- [ ] 대체 저장소 응답으로 실패·재개를 검증하고, 선택한 실제 저장소에서도 PNG와 MP4를 각각 확인한다.

완료 시 사용자는 파일을 따로 업로드하거나 URL을 복사할 필요가 없다. 기존 URL 직접 입력은 초기 문제 해결용으로 유지할 수 있다.

### IG-04 검수와 업로드와 예약 연결

기존 승인 버전 검사와 예약 요청 코드를 재사용한다. 사용자가 승인한 버전·계정·형식·캡션·카드 순서·예약 시간을 하나의 실행 기록으로 고정한다.

- [ ] 최종 화면에 실제 계정명, 선택한 형식, 완성본, 캡션, KST·미국 동부 시각을 보여준다.
- [ ] 사용자 게시 실행 후 업로드와 예약을 순차 처리하고 각 단계의 진행 상태를 표시한다.
- [ ] 서버에서 승인·제작·현재 버전 일치를 검사하며, 업로드 중 변경이 생기면 이전 승인으로 예약하지 않는다.
- [ ] 파일 확인 후 예약 시간이 이미 지났다면 새 시간을 입력하도록 안내한다.
- [ ] 캐러셀과 릴스를 별도 요청으로 처리하고, 형식별 성공·실패를 독립적으로 보여준다.
- [ ] Buffer 원격 게시 ID와 예약 접수 결과를 저장한다. `sent` 확인 전에는 게시 완료로 표시하지 않는다.

예약 시각은 UTC로 전달하며, 예약 접수와 실제 게시 성공을 구분한다. [Buffer 게시와 예약](https://developers.buffer.com/guides/posts-and-scheduling.html)

### IG-05 실패 복구와 중복 게시 방지 보완

기존 `unknown` 처리와 중복 요청 차단을 확장한다. 무조건 재전송하는 버튼을 추가하지 않는다.

- [ ] 업로드 실패, 명확한 예약 거절, 응답 불확실, 게시 실패, 조회 실패를 별도로 기록한다.
- [ ] 같은 작업을 두 번 누르거나 동시에 요청해도 동일 콘텐츠를 중복 예약하지 않는다.
- [ ] 예약 요청 전 상태를 저장하고, 전송 중 앱 종료·응답 손실 시 원격 생성 여부를 먼저 확인한다.
- [ ] 원격 생성 여부가 불확실하면 `unknown`으로 남기고 게시 ID 연결 또는 확인 절차를 안내한다.
- [ ] 원격 생성이 없다고 확인된 실패에 한해 기존 실패 기록을 보존하면서 재시도할 수 있다.
- [ ] Buffer에서 캡션이 수정된 경우 변경을 표시하되, 이미 연결된 게시물의 상태 조회 자체가 계속 막히지 않도록 보완한다. 다른 채널의 게시물 연결은 차단한다.
- [ ] 인증·요청 제한·일시 장애를 구분하고 읽기 재시도는 횟수·간격을 제한한다. 원격 오류에서 자격 증명을 노출하지 않는다.

검증 사례: 첫 파일 성공 후 업로드 실패, 요청 연속 클릭, 업로드 중 원고 수정, Buffer 성공 후 응답 끊김, 전송 중 재시작, 다른 채널 ID 연결 시도.

### IG-06 캐러셀과 릴스 실제 게시 검증

검수한 콘텐츠로 두 형식을 각각 게시한다. 처음부터 임의의 테스트 문구를 운영 계정에 올리지 않고, 기존 완성본 확인 절차를 사용한다.

- [ ] 실제 AI 응답으로 뉴스·책 근거가 연결된 초안을 만들고 원고·최종 캡션을 확인한다. 이 호출 검증은 기존 미검증 항목의 해소로 기록한다.
- [ ] 캐러셀 1건의 업로드·예약·실제 게시를 확인한다. 카드 순서, 잘림, 캡션, 계정을 점검한다.
- [ ] 릴스 1건의 업로드·예약·실제 게시를 확인한다. 세로 화면, 자막, 길이와 재생을 점검한다. 현재 릴스는 무음이다.
- [ ] 각 게시물의 로컬 작업 ID·버전, Buffer ID, 예약 시각, 게시 확인 시각, 실제 링크를 기록한다.
- [ ] 게시 후 새로고침과 앱 재시작에도 같은 결과가 표시되고 중복 게시가 발생하지 않는다.
- [ ] 대체 응답 테스트 결과와 실계정 결과를 분리해 M1 완료 여부를 기록한다.

### IG-07 게시 상태 자동 조회와 재시작 복구

현재 RSS에만 적용된 반복 실행을 게시 확인에도 확장한다. 앱이 중단된 동안 조회하지 못한 항목은 다음 실행에서 다시 확인한다.

- [ ] 아직 종결되지 않은 원격 게시물의 상태를 주기적으로 조회하고 마지막 성공·다음 조회 시각을 저장한다.
- [ ] 재시작 시 필요한 조회를 재개한다. 중단된 예약 생성 요청을 새 요청으로 자동 재전송하지 않는다.
- [ ] 조회 오류만으로 기존 예약 또는 게시 성공을 실패 상태로 덮어쓰지 않는다.
- [ ] 종료 상태와 재확인 대상 기준을 정의하고 중복 조회 작업을 합친다.
- [ ] 긴 AI 생성이나 영상 제작 때문에 게시 확인이 계속 밀리지 않도록 현재 단일 실행 대기열을 검토한다.
- [ ] 앱 종료 중에도 이미 접수된 예약은 Buffer가 처리하며, 로컬 상태 갱신은 앱을 다시 실행해야 한다는 점을 화면과 안내에 표시한다.

초기 게시 확인 간격은 5분을 제안하되 API 요청 제한과 실제 사용량에 맞춰 조정한다. 이는 공식 권장 주기가 아니다. PC가 꺼져 있어도 수집·제작·조회가 계속되는 상시 서버 운영은 별도 범위다.

### IG-08 실제 성과 수집과 주기적 갱신

현재 수동 `sync()`와 성과 저장 구조를 확장한다. 게시 상태 확인과 지표 갱신의 실행 주기를 나눈다.

- [ ] 게시 완료된 캐러셀·릴스에서 실제 반환되는 지표를 각각 확인하고 지원 범위를 기록한다.
- [ ] 지표 종류·값·단위, 제공자 갱신 시각, 앱 조회 시각을 보존한다. 0, 미제공, 미갱신을 구분한다.
- [ ] 초기 지표 수집 주기는 일 1회로 제안한다. 수동 새로고침도 유지하며 같은 갱신 결과를 중복 누적하지 않는다.
- [ ] 게시 확인 시각을 실제 게시 시각으로 오인하지 않는다. 실제 게시 시각을 얻을 수 없으면 그 한계를 표시한다.
- [ ] 같은 형식·비교 가능한 게시 경과 시간의 데이터로 분석하고, 충분하지 않으면 비교를 유보한다.
- [ ] 갱신 지연·지표 없음·인증 실패·요청 제한 사례를 테스트하고 실제 지표 1회 이상 수집을 확인한다.

Buffer 공식 문서상 게시 지표는 개인 API 키를 사용하며 일 단위로 갱신돼 첫 제공까지 약 24시간이 걸릴 수 있다. 배열에 없는 지표를 0으로 채우지 않는다. [공식 성과 문서](https://developers.buffer.com/guides/post-metrics.html)

### IG-09 연결 계정 선택과 설정 안내 화면

키 입력 후 연결된 Instagram 계정을 찾아 선택하도록 개선한다. 첫 실제 게시의 필수 조건은 아니지만 반복 운영에서는 채널 ID 수동 입력을 줄인다.

- [ ] 사용자가 접근할 수 있는 조직과 Instagram 채널을 조회하고 계정명·연결 상태를 표시한다.
- [ ] 사용할 계정을 명시적으로 선택해 저장하며, 첫 번째 계정을 자동으로 게시 대상으로 정하지 않는다.
- [ ] 기존 `.env` 채널 ID와 화면 설정의 우선순위를 정하고 서로 다른 계정을 가리키면 안내한다.
- [ ] 키 입력 여부, 실제 연결 확인 여부, 파일 저장소 준비 상태를 별도로 표시한다.
- [ ] 이미 생성한 게시 요청의 대상 계정은 이후 설정 변경으로 바꾸지 않는다.
- [ ] 서버 응답·브라우저 저장소·로그에 API 키와 저장소 비밀 키가 포함되지 않는지 확인한다.

### IG-10 운영 안내와 M2 통합 검증

## 5. 사용자 준비 사항과 개발자가 진행할 일

| 사용자 준비 | 프로그램에서 진행할 일 |
|---|---|
| Buffer 가입, `kostolany.wisdom` 로그인·권한 허용 | 연결 조회, 게시 계정 표시, 설정 오류 안내 |
| Buffer 개인 API 키를 로컬 환경에 입력 | 서버에서 키를 읽어 API 호출 |
| 저장소 제공자 선택, 계정·자격 증명·공개 주소 준비 | 자동 업로드, 원본 확인, 이력·URL 재사용 |
| 게시할 완성본·계정·형식·시각 확인 | 승인 버전의 예약 처리와 중복 방지 |
| 프로그램을 실행해 두기 | 게시 상태·지표 주기 조회와 재시작 시 복구 |

책 전체 입력은 기존 자료실 기능을 사용한다. 책 내용을 모두 입력해야만 게시 연동 개발을 시작할 수 있는 것은 아니다. 미디어 저장소 비용 조건과 상시 실행 환경은 사용 전에 결정한다.

## 6. 이번 범위에서 제외하는 기능

- Instagram 공식 API 직접 연동, 자체 Meta 로그인·토큰 관리
- 여러 사용자·고객 계정을 운영하는 서비스와 공개 관리자 사이트
- 사람의 최종 검수를 생략하는 자동 게시
- 음성 합성·배경음악·실사 영상·Instagram 공동작업자 기능
- PC가 꺼져 있어도 계속 작동하는 서버 배포
- 국가별 독자 통계나 모든 성과 지표 제공을 전제로 한 분석

이 항목들은 별도 요구가 생기면 백로그에 추가한다. 특히 현재 로컬 앱을 그대로 인터넷에 공개하는 것은 이번 미디어 파일 호스팅 작업에 포함되지 않는다.

## 7. 진행 상태 갱신 규칙

작업 상태는 `미착수 → 진행 중 → 로컬 검증 완료 → 실연동 검증 완료`로 기록한다. 외부 연동이 없는 작업은 로컬 검증으로 완료할 수 있다. 외부 연결이 필요한 작업은 코드 작성만으로 실연동 완료로 바꾸지 않는다.

| 기록 항목 | 남길 내용 |
|---|---|
| 구현 | 변경 커밋, 구현 범위, 미구현 사항 |
| 로컬 검증 | 실행한 검사와 결과, 대체 응답 사용 여부 |
| 실계정 검증 | 확인일, 대상 계정, 형식, 게시물 링크, 실제 지표 갱신 결과 |
| 남은 조건 | 필요한 설정, 재현되는 실패, 다음 작업 |

공개 저장소에는 비밀 키·책 원문·개인 계정 정보가 포함된 응답을 올리지 않는다. 실제 게시물 링크와 계정 연결 확인 결과만 필요한 범위로 남긴다.
